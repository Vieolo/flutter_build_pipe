# Migrating from < 0.4.0 to >= 0.4.0

Version 0.4.0 introduces these breaking changes, to the config, to the run order, and to the format of the output:
- Replacing `print_stdout` with `output`
- Changing the structure of the output, both in terminal and the log files
- Replacing `pre_build_command` and `post_build_command` with `pre_platform_run` and `post_platform_run`
- Running the platforms in a fixed order, starting with Android


## 1. Replacing `print_stdout` with `output` 
`print_stdout` was used to print all the output of the commands to the terminal.

It has been replaced with `output`. To replicate the behavior of the previous flag, you can set it to `verbose`.

`print_stdout` is no longer read and has no effect. While it is still in your config, a warning pointing to this guide is shown.

```yaml
# before
print_stdout: true

# now
output: verbose
```


## 2. Structure of the output
The structure of the output to terminal and the structure of the log files are changed.

If you had relied on their on the structure of their output, you'd need to update your logic.


## 3. Replacing `pre_build_command` and `post_build_command`
`pre_build_command` and `post_build_command` are replaced by `pre_platform_run` and `post_platform_run`, which have separate hooks for the `build` and `publish` commands.

The old keys are no longer read. A workflow that still has them stops with an error before anything runs.

`pre_build_command` becomes `pre_platform_run.build`:

```yaml
# before
pre_build_command: dart run build_runner build

# now
pre_platform_run:
  build: dart run build_runner build
  publish: dart run pre_publish.dart
```

`post_build_command` used to run after the builds, whether they had failed or not. It now has two replacements, and you need to choose the one that fits your command:

- `on_success` runs only when nothing has failed, e.g. for uploading or announcing a release
- `finally` runs whether anything has failed or not, e.g. for cleaning up

```yaml
# before
post_build_command: sh ./post-build.sh

# now, if the command should only run after successful builds
post_platform_run:
  build:
    on_success: sh ./post-build.sh
  publish:
    on_success: sh ./post-publish.sh

# now, if the command should run after the builds in any case, as before
post_platform_run:
  build:
    finally: sh ./post-build.sh
```

A `finally` command can check `BUILD_PIPE_STATUS` and `BUILD_PIPE_SUCCEEDED_PLATFORMS` to see what has succeeded. Read about the hooks of each platform, and the env variables given to the hooks, in the [hooks & run order doc](../hooks/hooks_intro.md).


## 4. The order of the platforms
The platforms now always run in this order, for both `build` and `publish`: Android, iOS, macOS, Windows, Linux, and Web. Previously, iOS ran first.

If you relied on iOS being built before Android, e.g. in your post-build command, you'd need to update your logic.
